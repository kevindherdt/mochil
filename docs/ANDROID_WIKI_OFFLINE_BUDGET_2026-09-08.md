# Android wiki offline budgeting

## Finding

The offline page loader previously combined retained pages with each new four-page batch, encoded a bounded snapshot, then decoded the entire result to recover the retained prefix. This repeatedly processed earlier content and the vault tree while downloading a vault.

## Change

`WikiOfflinePageBudget` measures the empty snapshot once and accounts for each new page using the same JSON page encoder as persistence, including UTF-8 bytes and array commas. The loader retains the accepted prefix directly, making those pages read-only without serializing and reparsing them. Final storage still performs its independent encoding and size checks.

Limits remain 3,000,000 payload bytes, 128 pages, 5,000 entries, and 2,000,000 characters per page. Invalid or oversized snapshot metadata fails before fetching pages. Network concurrency remains four; the first non-fitting batch ends fetching, and page order/progress semantics remain intact.

For 128 fitting pages in four-page batches, the old loop supplied 4 + 8 + … + 128 = 2,112 page occurrences to its budgeting encoder, plus 32 full snapshot decodes. The new budget checks 128 page occurrences and does no snapshot decoding. This is an algorithmic work-count comparison, not measured wall-clock or RAM savings. Device profiling remains outstanding.

## Verification

- Tests compare the accepted prefix against the persisted encoder for escaped and multibyte content.
- Tests cover page-count limits, invalid pages, excessive tree entries, large-page early stopping, small-page ordering/progress, and read-only results.
- Direct and Store debug unit-test tasks passed; Gradle completed in 38 seconds. This is test execution time, not an offline-download benchmark.
- Module checks passed.

No APK was published or container redeployed. No visual changes were made.

## Cancellation and fetch bounds

The page loader now enforces one to four pages per batch, consistent with the asset loader, and limits target fetching to 128 entries itself instead of relying solely on the mirror caller. With batches of three and excess targets, this prevents the last batch from downloading a 129th page that cannot be retained. It checks cancellation before initial progress and between page budget calculations.

Tests cover excess targets at batch size three, cancellation already requested at entry, and cancellation during a batch that still returns data. The latter verifies no subsequent progress or returned snapshot; it does not simulate cancellation during filesystem commit. Direct and Store unit suites each passed 675 tests with zero failures/errors, and module checks passed. No new APK or deployment.

## Encrypted cache boundary

Wiki snapshot stores now pass their 3,000,000-byte plaintext limit to `EncryptedPayloadStore`. Oversized writes return failure before encryption. Reads validate Base64 envelope length before decoding, ciphertext length (including the 16-byte authentication tag) before decryption, and plaintext length afterward. IVs must match the 12-byte format generated by this store. Other stores retain the default capacity; their envelopes receive the same structural checks. Invalid data returns no payload without deleting preferences.

This prevents additional unbounded decode/decrypt allocations for wiki snapshots. It does not bound Android's initial loading of the SharedPreferences XML/string itself; migrating large snapshots out of preferences is a separate possible improvement.

The isolated helper tests use actual JVM AES-GCM round trips at exact limits, empty content, padding slack, malformed Base64, bad tags, invalid IVs, and overflow-safe default-limit arithmetic. They do not exercise a physical device's AndroidKeyStore. The first run exposed a test-fixture IV shadowing mistake, corrected before rerunning. Both full Android variant suites passed 680 tests with zero failures/errors. Module checks passed. No APK or deployment.

## Selected-page retention

The merge previously sorted only by page download timestamp. Since mirrors fetch the selected page first, later downloads could take priority over it when retention limits applied. Merge now first resolves the newest copy per page identity, then prioritizes the latest snapshot's selected path before count/byte trimming. Remaining pages retain recency order. Cross-vault exclusion and newer-snapshot tree/selection ownership remain unchanged.

Two new tests cover a first-downloaded selected page surviving the 128-page cap and surviving byte trimming while retaining its newer revision rather than a stale cached copy. Both Android variant suites passed (682 tests per variant), and module checks passed. This does not make oversized individual pages cacheable or establish rename identity across path-based IDs. No APK or deployment.
